# 软件开发工作流

[返回仓库目录](../../README.md)

这条工作流连接项目文档入口、功能设计、领域建模、实施计划和知识收尾。按当前任务选择需要的技能；进入某个阶段不意味着必须运行后续全部阶段。每个技能的具体指令只在对应 `SKILL.md` 维护。

## 安装

安装 [Node.js 和 Git](../../README.md#命令安装) 后，为 Codex 安装这套工作流：

```sh
npx skills add RoversCode/xiaoliu-skills --skill project-docs-setup brainstorming domain-modeling planning-with-files-zh neat-freak --agent codex -g -y
```

将 `codex` 替换为 `claude-code` 或 `cursor` 可选择其他 Agent；省略 `-g` 则安装到当前项目。按名称选择这五个技能，仓库增加其他技能时不会自动扩大安装范围。

## 按任务进入

| 当前任务 | 进入方式 | 交付 |
|---|---|---|
| 项目缺少可用文档入口，或入口失效 | `project-docs-setup` | 经核实的概览与必要导航 |
| 功能行为、边界或验收存在实质歧义 | `brainstorming` | 与决策规模相称的设计；需长期交接时保存设计稿 |
| 需求明确的小修复、机械修改或单处文档修正 | 直接修改并做相关验证 | 已验证的修改；必要时同步受影响文档 |
| 已明确目标，需要跨会话恢复或管理多个相互依赖阶段 | `planning-with-files-zh` | 当前任务目录内的计划、发现与进度 |
| 用户明确要求持久化计划 | `planning-with-files-zh` | 与任务规模相称的文件记录 |
| 领域词义、边界或符合条件的重要决策变化 | 按需使用 `domain-modeling` | 相应术语或 ADR；没有变化则跳过 |
| 文档、规则与实现不一致，或需要交接/知识收尾 | `neat-freak` | 受影响权威文档与未闭合事项 |
| 只读审查、讨论或方案建议 | 在所选技能中保持只读范围 | 发现与建议；不因后续步骤包含写入而自动执行 |

工具调用次数、文件数量或阶段名称不单独触发设计讨论、三文件计划、独立评审或全套测试。已经清楚且获准的任务可以直接实施；已有设计无需换成另一份同内容文档再批准。

## 包含的 Skills

- [project-docs-setup](../../skills/project-docs-setup/SKILL.md)：建立或修复项目文档入口。
- [brainstorming](../../skills/brainstorming/SKILL.md)：解决会影响行为与验收的设计问题。
- [domain-modeling](../../skills/domain-modeling/SKILL.md)：维护项目特有术语、边界和必要的 ADR。
- [planning-with-files-zh](../../skills/planning-with-files-zh/SKILL.md)：为需要恢复和协调的任务保存执行状态。
- [neat-freak](../../skills/neat-freak/SKILL.md)：按影响范围对齐文档、规则和交接状态。

## 文档合同

| 内容 | 权威位置 | 何时保存 |
|---|---|---|
| 项目目的、使用方式与现有能力 | 现有 README / 项目文档 | 有已验证事实需要维护时 |
| 功能意图、范围与可观察验收 | 已确认需求、已有设计稿；新持久化设计默认 `docs/specs/YYYY-MM-DD-<topic>.md` | 确需跨阶段复核、交接或用户明确要求保存时；其余可在会话中明确 |
| 领域词汇与边界 | `CONTEXT.md`；确有多个上下文时用 `CONTEXT-MAP.md` 导航 | 新术语或词义澄清需要持久记录，且写入在授权范围内时 |
| 难逆转、需要解释且有真实取舍的决策 | 项目既有 ADR 目录，默认 `docs/adr/` | 符合决策记录条件且已确定时 |
| 当前任务的步骤、发现与执行证据 | `.planning/<feature>/` 中的三份文件，或项目明确的既有位置 | 当前任务确需持久化计划时 |
| Agent 必须遵守的约束与文档导航 | 当前平台实际加载的 `AGENTS.md`、`CLAUDE.md` 或等价规则 | 约束对后续工作确有作用时 |

已有项目布局优先。同一事实保留一个权威解释，其余位置引用；不为目录完整而创建空文档，不把当前项目的身份、路径或发布政策复制到其他项目。公开与本地文档的跟踪范围由具体项目决定。

## 阶段之间怎样衔接

读取当前决定所需且存在的材料，复用本会话已经读过、仍然有效的内容。只有会影响当前判断的缺失证据才需要说明；文档不存在本身不构成等待或补写要求。

用户已确定的需求、行为和授权在范围未变时持续有效。需要用户输入时，先准备具体问题，只暂停依赖该答案的部分，继续独立工作。阶段转换、失败次数和重新调用技能本身不构成再次确认的理由；用户或项目明确要求的特殊审批点仍然适用。

设计明确后，已获准的实施可以继续；需要跨会话恢复、管理多个相互依赖阶段，或用户明确要求保存计划时，再进入文件计划。实施后，存在受影响的长期文档或交接要求时再做知识收尾。验证根据实际改动选择，并复用代码、输入与环境未变时的有效证据；最终报告区分已验证结果和仍需验证的部分。

技能可以配合其他开发、调试或评审工具使用，但安装本工作流不意味着每次任务都要加载额外流程。跨任务整合产生新的风险时再补相应检查。

## 本地版本与迁移

以本仓库为这五个技能的维护来源。更新前核对本地同名技能的来源与差异，保留本地独有修改的恢复副本，再安装所选版本；不要把不同来源的同名目录混合成一个版本。其他来源的技能由各自来源维护。

`project-docs-setup` 承担本工作流的文档初始化职责。`setup-matt-pocock-skills` 的 issue tracker / triage 配置属于另一项用途；已有相关项目配置继续有效。不要因安装新版文档技能而自动删除旧技能或覆盖项目的 issue tracker 选择。
