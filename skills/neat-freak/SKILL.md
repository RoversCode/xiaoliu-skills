# 项目知识收尾

让受影响的项目知识与当前实现一致。只处理本次相关的文档、规则和已授权收尾，不把每次开发结束都变成全项目审计。

## 先确定工作模式

- **只读审查**：用户要求“看看、审查、审计、报告”时，只分析并报告。即使是明显笔误或安全可逆的小修，也不据此写入文档、规则、记忆或执行清理。
- **同步或交接**：本次确有文档/规则需要同步，或用户要求知识收尾、交接时，按已授权范围更新。普通小修且知识没有变化时，不自动启动本 skill 的整套流程。

用户和项目明确规定的更严格检查点始终保留，包括“汇报结果后再确认删除”等阶段性要求。

## 选择范围与证据

从本次需求、差异和已有结论确定受影响的知识面，只读相关权威文档与实际生效的规则；会话中已读且未变化的内容直接复用。不要先通读设计、计划、README、架构、CONTEXT、全部 ADR 或所有平台规则。缺少入口时再定向查找，[变更影响矩阵](references/sync-matrix.md) 仅作按需路由。

对重要差异保留：当前事实来源 → 过期说法 → 修改位置或建议 → 验证依据。代码和配置能证明实现内容；“已部署”“用户已经看到”需要对应运行证据。只把本次相关且无法确认的事实标为 `pending`；无关面不强行检查或填表。发布、多环境或清理涉及额外风险时再读 [证据与终态](references/verification.md)。

确需机械盘点时运行：

```bash
bash <本 skill 所在目录>/scripts/audit-inventory.sh <project-root> \
  --exclude <project-relative-directory> --exclude <another-directory>
```

`--exclude` 可省略或重复，按项目相对目录的字面路径匹配；不存在的目录也可预先排除。脚本默认在所有层级排除 `ref_code`、依赖、构建缓存和 `.git`，遍历前剪枝，不跟随目录或文件软链。它只盘点指定项目，不默认扫描祖先规则、用户目录或其他平台；那些范围确有必要时另行明确范围并定向读取。无需盘点时不运行脚本。

v3 保留单个 `<project-root>` 调用方式和 Markdown 清单/计数等区段，但输出不与 v2 完全相同：Git 区段仅含 `git_root`、`branch`、`head`，移除了 `status_entries`、`worktrees` 和全局 `platform-directories`；规则候选和根条目也只包含排除后的项目范围。Git 状态、worktree 和加载顺序按实际任务另查。脚本输出路径及规则统计，不能替代阅读相关内容；不支持 Bash 的环境可做等价只读盘点。

## 同步与清理

1. 在既有权威文档就地修正过期事实，合并本次遇到的重复解释。保留仍有用途的历史和回退说明；不为统一形式重排无关文档。
2. 领域词义或上下文边界变化时使用 `domain-modeling`；只有符合其条件的决策才写 ADR。长期结论不只留在执行记录里。
3. 相关规则只保留必须遵守的边界、命令和文档入口。加载关系不清时按需读 [平台规则](references/agent-paths.md) 或 [规范审计](references/governance.md)；不自动创建第二份规则文件、额外 hook 或审计门禁。
4. 已有计划且需要记录交接时复用它，按任务核实验收和待办，不为收尾再建一套计划。仅当用户或项目授权维护 Agent 记忆时处理相关条目；平台生成内容遵循宿主机制，机制不明时只读。
5. 需要清理时核对对象、唯一未集成内容和有效授权。已有具体授权继续有效；除当前范围超出授权、对象状态变化或明确检查点要求外，不重复询问。只有“收尾/整理”而未明确清理范围时，先给可复核清单，再请求必要授权。不能凭目录名、年龄或“已完成”字样判断可删除。

外部发布、迁移、代发等仍遵守当前环境和用户授权，收尾本身不扩大权限。

## 验证与报告

复用仍对应当前代码、配置、输入和环境的有效验证证据；相关内容变化、既有证据不足或风险要求时，才补跑适用的链接检查、测试、构建或运行路径。用户/项目明确要求的检查仍需满足。不因收尾阶段机械重跑全套测试，也不为无关面制造 `pending`。

最终说明审查发现或实际改动、证据支持的状态、相关待确认项及本次未覆盖范围。只读审查不声称已修复；文档同步不推导代码、部署或整个工作区均已完成。
