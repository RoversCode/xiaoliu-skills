# 领域建模

这是设计或实施中的按需活动，不是固定关卡。只读相关且存在的领域记录与代码；会话中已读且未变的内容直接复用，缺少 `CONTEXT.md`、`CONTEXT-MAP.md` 或 ADR 不要求补空壳、逐项登记缺失。

仅请求分析或建议时，在会话中澄清词义和取舍，不写文件。已授权的开发或文档维护确实改变领域事实时，同步对应权威记录即可，不重复索取已有授权。

## 澄清与记录

- 术语含糊或一词多义时，用具体业务场景区分概念；与现有术语冲突时指出并解决冲突。只对无法从证据判断、需要用户决定的部分提问，继续不依赖答案的已授权工作。
- 检查用户描述与代码、数据和真实行为是否一致。不能确定的事实留待验证，不把猜测写成定义。
- 词义确定且需要持久记录时，在授权范围内更新权威位置，参考 [CONTEXT 格式](references/context-format.md)。只记录项目特有词汇与边界，不放实现步骤、功能验收或架构流水账。已有布局优先；无布局且确有内容时，单上下文项目可用根目录 `CONTEXT.md`，多个独立领域上下文可用 `CONTEXT-MAP.md` 导航到各自的词汇表。
- 只有决策难逆转、若不解释会令人意外、且确实比较过不同取舍时，才在授权范围内写 ADR。沿用项目 ADR 位置；没有约定时用 `docs/adr/`，格式见 [ADR 格式](references/adr-format.md)。更改既有决策时标清取代关系，尚未确定的取舍不能写成已接受决定。

## 交接

核对修改后的定义与实际行为、已有决策是否一致，并检查改动的链接；无需为记录词义额外制造测试。确有设计稿或计划时引用权威定义，不复制长篇内容。完成领域变更即可继续原任务，不默认启动设计、计划或收尾技能；没有真实领域变化或符合条件的决策时，不制造文档。
