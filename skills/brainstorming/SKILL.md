# 功能设计讨论

目标是把尚不清楚的想法变成能指导实现和验收的设计。讨论深度与决策风险相称；用户已经提供的决定视为有效输入，不重复要求确认。

## 讨论

1. 先读项目的 README、相关设计稿、`CONTEXT.md` 或 `CONTEXT-MAP.md`、相关 ADR 和代码现状。区分已实现行为与新想法。
2. 找出会改变方案或验收的少数歧义。优先问目标用户、关键场景、范围边界、约束和成功标准；能从现有材料可靠推断的细节直接处理。
3. 真实存在取舍时给出可比较的方案和推荐理由。没有有意义的替代方案时，不强凑选项。
4. 用具体场景检验行为、异常和边界。讨论中出现新的领域词汇、上下文边界或重要决策时，调用 `domain-modeling`，把词义或 ADR 写到其权威位置；设计稿只引用结论。
5. 对会改变产品行为、范围或外部承诺的决定，向用户呈现具体设计并取得所需确认。用户对关键行为和范围的回答已经构成确认时，直接整理设计与实施交接；不要再要求一次形式化批准。

## 设计稿与交接

沿用项目现有设计文档位置；没有约定时写到 `docs/specs/YYYY-MM-DD-<topic>.md`。设计稿至少让实施者找到：问题与目标、范围和不做的事、关键用户流程或系统行为、可观察的验收标准、约束、已决定的取舍，以及相关 `CONTEXT.md` / ADR 链接。篇幅随复杂度变化，不填空洞章节。

写完检查设计稿是否自相矛盾、是否把未实现能力写成现状、验收是否可验证。有阻止实施的未决问题时继续澄清；非阻断问题明确标出。将设计稿路径、验收标准和已确定的约束交给 `planning-with-files-zh`。若项目尚无清楚的文档入口，可先用 `project-docs-setup` 补齐；不要转给本仓库不存在的规划 skill。
