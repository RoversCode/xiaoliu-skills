# 功能设计讨论

把尚不清楚的想法变成能指导实现和验收的决定。讨论深度与风险相称；已明确的小任务直接在授权范围内实施，不补设计仪式。用户已经提供或批准的决定持续有效，除非新证据使其失效，不重复确认。

## 讨论

1. 只读与当前歧义相关且存在的项目材料和代码，区分现有行为与新想法。会话中已知且未变的内容直接复用；缺少设计稿、领域词汇或 ADR 不要求补建，也不逐项标记待补。
2. 找出会改变方案或验收的少数歧义。只问需要用户作出的选择；能从现有材料可靠推断的细节直接处理，并在影响结果时说明假设。提问只暂停依赖答案的部分，其他已授权工作继续。
3. 真实存在取舍时给出可比较的方案和推荐理由。没有有意义的替代方案时，不强凑选项。
4. 用具体场景检验关键行为、异常与边界，不为简单改动制造完整测试清单。只有真实术语、领域边界或符合 ADR 条件的决策变化时，才需要 `domain-modeling`。
5. 将仍需用户决定的取舍呈现为具体结果，取得当前授权尚未覆盖的决定；用户的回答已确定关键行为和范围时直接采用。只读分析或方案请求不授权写文件或实施；已有实施授权则在澄清后继续，不再安排一次形式化批准。

## 设计稿与交接

默认在会话中说明目标、范围、关键行为、可观察的验收标准和必要取舍即可。重大工作确需跨阶段复核或交接，或用户明确要求保存设计时，在授权范围内沿用现有设计位置；没有约定时可用 `docs/specs/YYYY-MM-DD-<topic>.md`。只写实际需要的信息，引用相关且存在的领域记录，不填空洞章节。

检查结论是否自相矛盾、是否把未实现能力写成现状、验收是否可验证。已授权实施且不存在依赖阻塞时继续执行；用户只要方案时交付方案。只有跨会话恢复、多个依赖阶段或用户明确要求文件计划时，才考虑 `planning-with-files-zh`；文档入口缺失不自动触发 `project-docs-setup`，也不阻止独立可完成的工作。
