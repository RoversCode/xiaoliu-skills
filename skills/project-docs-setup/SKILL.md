# 项目文档初始化

把已核实的项目事实整理成容易找到的文档入口，沿用已有布局，只补影响使用的缺口。仅要求检查或给建议时，在会话中报告结果；初始化或修复文档得到授权后再写文件，不把首次接手当成写入授权。

## 先看现场

先看实际生效的项目规则与现有文档入口，再按本次要修复的问题读取相关且存在的 README、索引、设计、领域词汇或 ADR；需要核实事实时才查看对应代码与配置。会话中已读且未变的内容直接复用，不重读整套材料。确认现有文件各自承担什么职责，避免另建平行答案。缺少文档本身不是故障，不补空壳，也不逐项列待补清单；只指出会影响当前判断的事实缺口。

## 建立入口

1. 用现场证据核实要写的项目目的、现有能力或使用方式。只问阻止准确落笔的问题，并继续处理不依赖答案的部分；已确定的决定不再确认，尚未实现的能力明确标为计划。
2. 在已有 README 或概览中补足必要的定位与导航。确需入口且没有可复用文件时，创建简短 README；只写有证据的事实和有用链接。
3. 沿用项目文档路径与跟踪规则。无约定且确需相应文档时，可用 `docs/specs/` 存设计、根目录 `CONTEXT.md` 存领域词汇、`docs/adr/` 存重要决策、`.planning/<task>/` 存任务计划；这些不是必须建齐的目录。
4. 需要 Agent 导航时，在实际生效的规则文件中说明：按任务读取相关且存在的材料，复用会话上下文，实际改变长期事实时同步对应文档。没有规则文件时，只在导航确有价值且属于授权范围时创建当前平台原生文件，不另设一套规则。
5. 核对本次新增或修改的链接、路径和事实即可；未受影响且仍有效的检查结果可以复用，不为文档整理额外运行全套测试。

## 与其他 skill 的边界

本 skill 只处理文档入口与布局。确有产品取舍时才用 `brainstorming`，有真实术语或重要决策变化时才用 `domain-modeling`，任务确需持久计划时才用 `planning-with-files-zh`。不要把任务进度复制进 README，也不把 `neat-freak` 或其他技能设为默认下一站；入口修复完成即可汇报结果。
